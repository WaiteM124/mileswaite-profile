RAG Platform: Retrieval Under Production Constraints

A public, multi-collection RAG platform built to show what changes when retrieval-augmented generation has to run as a production service, with a budget, an attacker model, a release gate and licensing obligations.

23 November 2026

A new system is being built alongside the essays on this site: a public, multi-collection retrieval-augmented generation (RAG) platform, deployed at rag.mileswaite.net. Its purpose is narrow and deliberate. Most RAG systems in public view are demos, a vector store, a prompt and a chat box. This one is built to show what changes when the same idea has to run as a production service, with a budget, an attacker model, a release gate and licensing obligations.

The architecture runs on AWS in eu-west-2. Documents are embedded with Amazon Titan v2 through Bedrock and stored in Postgres with pgvector on RDS, so retrieval sits in the same transactional database as the metadata that governs it. A FastAPI backend streams answers to a React and TypeScript front end, and the services run on ECS Fargate on ARM64 behind a load balancer. All infrastructure is defined in Terraform, with separate roles for planning and applying changes. Deployments go through GitHub Actions using OIDC, which means short-lived credentials and no stored cloud keys.

The more interesting engineering is in the controls. Rate limits are applied per IP using the rightmost X-Forwarded-For hop, the one the load balancer appended, because the leftmost value is supplied by the client and can be forged. A hard daily spend cap of £2 bounds the cost of any misuse. The platform also sets strict security headers and a content security policy, scales from one to two tasks, and raises CloudWatch alarms on server errors. Merges are gated in CI on Ragas evaluations run separately for each collection, so a change that degrades retrieval quality on any collection cannot ship.

Retrieval is also licence-aware. Full text is returned only from sources under the Open Government Licence or CC BY. For everything else the system returns an excerpt and a link to the original. In this design, what a model may reproduce is decided before generation, by metadata, not left to the model.

The first collection is Complex Systems, followed by UK Tax, covering HMRC and GOV.UK guidance on VAT, Making Tax Digital and IR35. Content ingestion is still pending, so the platform does not yet answer questions.

Planned next are diagrams and graphs generated from retrieved evidence, so that an answer about a feedback loop or a tax decision path can be shown as a structure, not only described in prose. This is planned work, not yet implemented.

Building it has already produced lessons, all of them ordinary and instructive:

  • A new AWS account's free-plan limits refused seven-day database backups.
  • An amd64 container image failed on ARM64 Fargate.
  • pgvector rejected a comparison between a vector and a double-precision array.
  • Terraform state kept in CloudShell was wiped and had to be rebuilt by importing 13 resources.
  • Autoscaling failed for lack of a service-linked role.
  • The infrastructure and application pipelines raced each other until they were chained explicitly.

None of these is a model problem. That is the point the platform is built to make.

Evaluation scores and cost figures will be published once they are measured.
